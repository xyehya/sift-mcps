System in one paragraph

The Gateway is the single policy boundary: every REST call, every MCP tool call, every privileged action passes through it. Postgres is the authoritative control plane (RLS-forced); OpenSearch is derived and never authoritative. AI agents reach 42 tools across 6 backends only through the aggregate /mcp; humans use the React portal at /portal. Heavy work runs as durable Postgres jobs claimed by least-privilege workers, and deep execution is confined to an OS-sandboxed run_command plane with 27 fail-closed security controls across the 10-stage MCP tool-call chain.

VP-1 C4 Model · Level 1 — System Context

Who and what the gateway serves

Scope & external interfaces: the system is a single trust-bearing unit with exactly two classes of consumer and one external dependency. There are no other ingress paths.

Only two consumer classes exist — a human operator over HTTPS to /portal, and an AI agent over MCP to /mcp. Both terminate at one system. The lone external dependency, OpenCTI, is reached through the gateway under a query-only contract — the agent never talks to it directly.

VP-2 C4 Model · Level 2 — Containers / 8 Planes

The eight planes and the one gate between them

Decomposition & authority: how runnable units split into planes, which plane is the source of truth, and the fact that every path from a client to anything privileged is funneled through a single gold band. Color encodes plane authority (see key).

The gold band is the only thing both clients can reach, and everything below it is reachable only from inside that band. Authority flows one way: Postgres (blue) is the source of truth; OpenSearch (teal) is a derived projection rebuilt from artifacts and never trusted as the system of record. Heavy work doesn't block the agent — the gateway enqueues a durable job, least-privilege workers claim it under a lease, and confined execution writes results back up to Postgres and out to the derived index. Evidence (green) uses a Portal-authorized local-protected or descriptor-pinned external-read-only profile; reports contain only approved material.

VP-3 UML 2.5 · Sequence — 10-Stage Tool-Call Policy Chain

One ordered path, ten fail-closed gates

Runtime security behavior: the exact ordered chain every agent tool call traverses (verified in policy_middleware.py + mcp_server.py). A deny at any stage short-circuits to an audited MCP error — the tool body never executes.

Identity is resolved before the chain even begins, and stages 1–10 run in fixed order. Six of them can reject outright (dashed red). Stage 1 — ControlPlaneRequired (BU3) — is the outermost backstop: no control-plane DSN means no DFIR tool can reach file-authority readers. Stage 7 — EvidenceGate — is the hard interlock: no tool touches a case until its evidence is registered, sealed, and the custody chain verifies. Only a call that clears all ten reaches the tool body, and even its output is redacted on the way back out.

VP-4 STRIDE · Data-Flow Diagram + Threat Matrix

Trust boundaries and what guards each crossing

Threat exposure: where trust changes hands, what an adversary could attempt there (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), and the specific control that closes it. Seven boundaries; every flow crosses at least one.

The two boundaries a forensic system lives or dies on are #2 (evidence mutation is Portal-only; Postgres custody plus profile-specific posture and Full Verify detect drift) and #6 (tool output is treated as hostile and scrubbed before it re-enters the agent's context — the prompt-injection-from-evidence defense). Boundary #4 encodes the authority rule from VP-2: even a fully-authorized write lands in Postgres under RLS, never in the derived index.

VP-5 UML Deployment + Defense-in-Depth — run_command

The jail every forensic command falls through

Execution containment & deployment: where confined work runs (the SIFT VM node, as a dedicated runtime user) and the two stacked layers — a policy ceiling and a kernel floor — that a command must clear before a forensic binary ever executes. Both default to deny.

The ceiling reasons about intent — is this program allowed, does its text smuggle a shell, does the environment leak an interpreter — and the floor enforces capability at the kernel: even a command that talked its way past policy can't read outside the case paths (Landlock), can't make a disallowed syscall (seccomp kills it), can't reach the network or exceed its memory (cgroup), and can't regain privilege (no-new-privs). The defaults are deny on both layers, which is why the red-team rows fail without ever asking for approval.
